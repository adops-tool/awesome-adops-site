# Contributing to Awesome AdOps

Thanks for helping keep this directory useful to advertising operations, publisher, programmatic, and ad-tech teams. Contributions of standards, technical documentation, tools, open-source projects, learning resources, and communities are welcome.

## What belongs here?

A resource should have a clear, practical connection to digital advertising operations or the systems that support it. Good additions include:

- Ad servers, publisher monetization, DSPs, SSPs, exchanges, and header-bidding projects.
- Ad-tech standards, SDKs, APIs, open-source libraries, and technical documentation.
- Ad quality, privacy, consent, identity, measurement, and supply-chain transparency tools.
- Video, CTV, audio, mobile, retail media, creative, analytics, debugging, and campaign-operations resources.
- Useful training, industry news, communities, and reference material for ad-tech practitioners.

Prefer resources that are actively useful and have a clear, verifiable purpose. Avoid spam, unrelated general-purpose products, duplicates, dead links, referral links, and unsupported claims. Commercial resources are welcome when they are genuinely relevant; inclusion is not an endorsement. A tool may fit more than one topic, but list it once in the section that best describes its primary use.

## Entry format

Add a single Markdown bullet under the appropriate heading. Use one of the repository's five animated marker images and keep the category label consistent with nearby entries:

```markdown
- ![Header Bidding](image/dot_1.gif) [Resource Name](https://example.com/) - A concise, factual description of what it does.
```

Use the existing files `image/dot_1.gif` through `image/dot_5.gif`; vary the marker between adjacent entries. Do not add remote image URLs or duplicate image files.

## Style and review checklist

- Write entries in English and sort them alphabetically by displayed name within the section.
- Link directly to the official homepage, documentation, source repository, extension listing, or tool page.
- Use the resource's commonly recognized name and a short, neutral description (ideally one sentence).
- Verify the link and the description against the linked source; do not infer features that the source does not document.
- Check for duplicates, including entries in other categories. List a resource once, under its primary use.
- Prefer maintained projects and current product pages. Clearly mark archived or historical resources as such.
- Keep category labels, Markdown formatting, and marker paths consistent with the examples above.

## Pull requests

1. Edit `README.md` and update this guide only if the contribution changes the categories or conventions.
2. Explain why the resource is useful and why its category is appropriate.
3. Group related additions coherently and avoid unnecessary new sections.
4. Submit a pull request. Maintainers may adjust descriptions, placement, and formatting for consistency.

Prioritize the usefulness and accuracy of the list over its size; a resource should not be added simply because it exists.

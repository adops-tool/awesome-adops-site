# Contributing to Awesome AdOps

Thanks for helping make this directory useful to ad operations, publisher, programmatic, and ad-tech teams. Contributions of tools, documentation, standards, open-source projects, communities, and practical learning resources are welcome.

## What belongs here?

A resource should be relevant to digital advertising operations or the systems around it. Good additions include:

- Ad servers, publisher monetization, SSPs, DSPs, exchanges, and header-bidding projects.
- Ad-tech standards, SDKs, APIs, open-source libraries, and technical documentation.
- Ad quality, privacy, consent, identity, measurement, and supply-chain transparency tools.
- Video, CTV, audio, mobile, creative, analytics, debugging, and campaign operations resources.
- Useful training, industry news, communities, and reference material.

Prefer resources that are actively useful and have a clear purpose. Avoid spam, unrelated general-purpose products, duplicates, dead links, referral links, and unsupported claims. Commercial tools are welcome when they are genuinely relevant; inclusion is not an endorsement.

## Entry format

Add one Markdown bullet under the appropriate heading. Keep the animated marker pattern:

```markdown
- ![Category](image/dot_1.gif) [Resource Name](https://example.com/) - A concise, factual description of what it does.
```

Replace `Category` with a short label that matches the section (for example `Header Bidding`, `Privacy`, or `Video`). Use one of the five repository GIFs: `image/dot_1.gif`, `image/dot_2.gif`, `image/dot_3.gif`, `image/dot_4.gif`, or `image/dot_5.gif`. Vary the GIF used between adjacent entries so the list remains visually lively; cycling through 1–5 is an easy approach. The GIFs are animated and should be referenced by their existing relative paths—do not add remote image URLs or duplicate image files.

## Style guide

- Write entries in English.
- Link directly to the official homepage, documentation, repository, extension listing, or tool page.
- Use the resource's commonly recognized name and a short description (ideally one sentence).
- Be specific and neutral; do not use promotional superlatives.
- Place items alphabetically by displayed name within their category where practical.
- Check that the resource is not already listed and that the URL loads.
- For software repositories, link to the repository rather than a generic organization page whenever possible.
- Keep the existing section order unless proposing a clearer structure.

## Pull requests

1. Edit `README.md` and, if needed, this guide.
2. Include a brief explanation of why the resource is useful and where it belongs.
3. For several related resources, group them in a coherent category and avoid duplicates.
4. Submit a pull request. Maintainers may adjust descriptions, placement, or formatting to keep the list consistent.

There is no need to add a resource simply because it exists; prioritize usefulness, relevance, and clear descriptions.
